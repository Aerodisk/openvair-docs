## Документация модуля панели управления кластером (control-plane)

## API

**Control-plane API** — это «дверь» в мозг кластера. Через неё:

- ноды представляются системе (регистрация);
- ноды подают признаки жизни (heartbeat);
- платформа спрашивает совет, где запускать новую ВМ (placement);
- админ/мониторинг проверяют, жив ли сам control-plane (health);
- UI/CLI получают список нод и их статусы (nodes).

Все ответы идут в одном формате BaseResponse[...], чтобы фронт/cli не гадали, где статус, где данные и где ошибка.

## Зачем это нужно

1. Единая точка правды о кластере.
   Без control-plane каждая нода «сама по себе». С ним появляется реестр узлов и их состояния.
2. Переход от «одиночки» к кластеру.
   API — минимальный каркас, чтобы систему уже можно было запускать в кластерном режиме и дальше наращивать логику (
   планирование, миграции, HA).
3. Наблюдаемость и управляемость.
   Сердцебиения и реестр дают базовую картину здоровья кластера, на которую потом навешиваются оповещения и
   автоматические реакции.
4. Стабильный контракт для UI/CLI/интеграций.
   BaseResponse + Pydantic-схемы = предсказуемые ответы и внятные ошибки валидации.

## Где будет использоваться

- Web-UI / панель админа: рисовать список нод, их статусы, кнопки «зарегистрировать ноду», «проверить здоровье».
- CLI / автоматизация: скрипты регистрации ноды после установки агента; periodical job, шлёт heartbeat.
- Другие модули платформы: при создании ВМ модуль vm вызывает /cluster/placement, чтобы понять, на какой узел отправить
  задачу. (Возможно наоборот)

## Как это выглядит «в жизни» — 3 типовых сценария

### 1. Регистрация ноды
1. На новой машине ставится агент/сервисы.
2. Скрипт устанавливает соединение и вызывает POST /cluster/nodes/register с hostname, ip, roles, labels. 
3. Control-plane создаёт/обновляет запись ноды и отвечает NodeOut в BaseResponse. 
4. UI сразу видит ноду в списке.

### 2. Поддержание статуса (heartbeat)
1. Раз в N секунд агент ноды отправляет POST /cluster/heartbeat с node_id и (опционально) метриками.
2. Control-plane обновляет last_seen. 
3. Если heartbeats нет дольше порога — помечает ноду offline.
4.UI/мониторинг читают GET /cluster/nodes и видят актуальные статусы.

### 3. Размещение новой ВМ (placement)
1. Пользователь в UI создаёт ВМ (запрос уходит в бэкенд). 
2. Бэкенд формирует VmPlacementRequest (vcpu, ram_mb, labels) и вызывает POST /cluster/placement. 
3. Control-plane возвращает VmPlacementDecision (какую ноду выбрать и почему). 
4. Модуль compute отправляет задачу создания ВМ на выбранную ноду по вашему RPC.

## Роли схем
### Входные 
NodeRegisterIn, HeartbeatIn, VmPlacementRequest — валидируют, что пришло ровно то, что нужно (UUID, числа, словари). Ошибки валидации — читаемые.
### Выходные
NodeOut, VmPlacementDecision — стандартизированный ответ для UI/CLI.
`BaseResponse[T]` — единый «конверт»:
```python
status: "success"|"error"
data: T | null
error: str | null
```
Это упрощает фронту жизнь: всегда один шаблон разбора ответа.
