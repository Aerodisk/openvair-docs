# Тесты модуля notification

## Цели тестирования
- Проверка работы публичного API-эндпоинта модуля `notification`
- Обеспечение корректности валидации входных данных и бизнес-логики модуля
- Тестирование обработки ошибок инфраструктуры
- Документирование допустимого и ошибочного поведения системы
- Обеспечение устойчивости к рефакторингу через автоматизированные проверки

## Подход к тестированию
Тесты реализованы как **интеграционные**:

- Используется прямое взаимодействие с API через `TestClient`
- Проверяются как позитивные сценарии (успешная отправка), так и негативные (ошибки валидации, сбои)
- Тесты взаимодействуют с реальными компонентами: PostgreSQL (хранение уведомлений), RabbitMQ (RPC-вызовы)
- Все сценарии изолированы друг от друга

## Организация и инструменты
- `pytest`, `fastapi.testclient` — основной стек для тестирования
- Реальная БД PostgreSQL для хранения истории уведомлений и RabbitMQ для RPC-вызовов между слоями проекта
- Конфигурация через `.env.test` и `project_config.toml` с указанием SMTP-сервера и email-адресов получателей 
- Автоматическая очистка данных после каждого теста через соответствующую фикстуру


## Используемые фикстуры
- **notification**: Генерирует тестовые данные уведомления и очищает БД после теста
- **mock_auth_dependency**: Подмена JWT-аутентификации для авторизованных запросов
- **unauthorized_client**: Клиент без авторизации для проверки доступа
- **cleanup_all_notifications**: Фикстура очистки уведомлений в БД
- **client**: Стандартный тестовый клиент FastAPI с настроенной аутентификацией

## Покрытие эндпоинтов
| Эндпоинт                  | Назначение                     | Статус покрытия |
|---------------------------|--------------------------------|-----------------|
| `POST /notifications/send/` | Отправка уведомлений           | ✅ покрыт       |

## Ключевые тест-кейсы
1. **Успешная отправка email**:

     - Проверка HTTP 200 OK
     - Соответствие ответа отправленным данным
     - Проверка записи в БД (статус `"sent"`, дата создания)

2. **Ошибки авторизации**:

      - Доступ без токена → HTTP 401

3. **Валидация входных данных**:

     - Отсутствие обязательных полей (`msg_type`, `recipients` и др.) → HTTP 422
     - Неправильный формат `email`
     - Недопустимый тип уведомления

4. **Обработка ошибок инфраструктуры**:

     - Имитация ошибок сервисного слоя по RPC (RabbitMQ)
     - Имитация таймаутов соединения с сервисным слоем по RPC

5. **Пограничные случаи**:

     - Пустые значения `subject`/`message`
     - Отправка уведомления с длинным текстом (5000 символов)

## Инфраструктурные детали
- Реальные сервисы: PostgreSQL, RabbitMQ
- Перед тестами необходимо указать настроенный SMTP-сервер в `project_config.toml` 
  ([**Инструкция**](../../../user_guide/notification.md))
- Тестовые SMTP-получатели Email-уведомлений настраиваются через `.env.test`:
```
  TEST_NOTIFICATION_EMAILS=test@email.com,test2@email.com
  TEST_NOTIFICATION_TYPE=email
```
- Все тесты полностью изолированы и независимы друг от друга
- Автоматическая очистка БД после каждого теста

## Запуск тестов
```shell
cd openvair/modules/notification/tests/
pytest -v
```

## Примечания

- В текущей реализации тесты запускаются вручную после изменений в коде
- При необходимости могут быть легко встроены в CI/CD pipeline
