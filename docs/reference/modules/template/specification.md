# Документация модуля template


## Основное назначение

Модуль `template` отвечает за централизованное управление шаблонами томов (`volume templates`) в платформе виртуализации.  
С помощью шаблонов пользователи и администраторы могут создавать новые виртуальные тома (диски) на основе заранее подготовленных, стандартизированных образов (`qcow2`), что ускоряет развертывание типовых и корпоративных конфигураций, снижает вероятность ошибок, повышает однородность инфраструктуры.

Модуль реализован в соответствии с принципами DDD (Domain-Driven Design) и многослойной архитектурой — он изолирован, не зависит напрямую от других модулей, и его отказ не влияет на работу системы в целом. Архитектура включает отдельные подсистемы для веб-API, сервисного и доменного слоя.

---

## Функциональность

- Создание шаблонов из существующих томов.
- Хранение и учёт метаданных шаблонов: имя, описание, хранилище, формат, статус и пр.
- Получение и поиск шаблонов с поддержкой пагинации.
- Обновление метаданных шаблонов (имя, описание).
- Удаление шаблонов с проверкой связей и статусов.
- Возможность использовать шаблон как backing-файл для экономии места.
- Валидация входных данных и статусов.
- Стандартизированные ответы API.
- Поддержка событийной модели и RPC для интеграции с остальной системой.

---

## Архитектура

Модуль построен по DDD и layered-architecture:


> API (FastAPI) → Service Layer → Domain Layer → Infrastructure (ORM, Storage, DTO, Volume)


### Слои

- **API** — FastAPI эндпоинты, приём запросов, валидация и сериализация данных, маршрутизация, стандартизация ответа через обёртку.
- **Service Layer** — бизнес-логика модуля, промежуточная обработка, проверка прав, вызовы в domain-слой и внешние сервисы.
- **Domain Layer** — работа с сущностями шаблонов, правила и ограничения (например, нельзя удалить используемый шаблон), логика формирования backing-файлов.
- **Infrastructure** — реализация доступа к БД через ORM, RPC-интеграция (RabbitMQ), сериализация/десериализация DTO, работа с файловой системой и libvirt/qemu.

## Эндпоинты API

| Метод    | URL                             | Описание                                              |
|----------|---------------------------------|-------------------------------------------------------|
| `GET`    | `/templates/`                   | Получение списка шаблонов, поддержка пагинации        |
| `GET`    | `/templates/{template_id}`      | Получение информации о шаблоне по ID                  |
| `POST`   | `/templates/`                   | Создание нового шаблона                               |
| `PATCH`  | `/templates/{template_id}`      | Редактирование имени и/или описания шаблона           |
| `DELETE` | `/templates/{template_id}`      | Удаление шаблона по ID                                |

---

### Подробности по эндпоинтам

#### `GET /templates/`
- Возвращает: список шаблонов и метаданные пагинации (`items`, `total`, `page`, `size`, `pages`).
- Каждый элемент содержит: `id`, `name`, `description`, `tmp_format`, `storage_id`, `is_backing`, `created_at`, `status`.

#### `GET /templates/{template_id}`
- Возвращает: подробную информацию о шаблоне по UUID.
- При ошибке: возвращает статус 404, если шаблон не найден.

#### `POST /templates/`
- Создаёт шаблон на основе существующего тома.
- Требует обязательные поля: `name`, `storage_id`, `base_volume_id`, `is_backing`.

#### `PATCH /templates/{template_id}`
- Позволяет изменить имя и/или описание шаблона.

#### `DELETE /templates/{template_id}`
- Удаляет шаблон. Проверяет, не используется ли шаблон другими томами/ВМ.

## RPC

Модуль поддерживает асинхронное взаимодействие с другими сервисами через RPC (RabbitMQ).  
Вызовы между слоями (API ⇄ Service Layer ⇄ Domain) реализованы как удалённые процедуры.  
Модуль может реагировать на внешние события (например, завершение создания тома) и публиковать собственные (создание, удаление шаблона).

---

## Статусы шаблона (`TemplateStatus`)

- `available` — шаблон готов к использованию.
- `creating` — шаблон находится в процессе создания/импорта.
- `deleting` — шаблон помечен на удаление, происходит освобождение ресурсов.
- `error` — произошла ошибка при создании/удалении шаблона.

Статус используется для управления жизненным циклом шаблона, отображается в UI и API.

---

## Хранилища

Модуль работает с абстракцией хранилища (storage).  
Каждый шаблон связан с определённым хранилищем (`storage_id`), где физически находится его образ (`qcow2` или `raw`).  
Поддерживаются разные типы хранилищ: локальные, сетевые, распределённые (NFS, iSCSI и др. — если поддерживаются платформой).

---

## Валидации и исключения

- Все входные данные валидируются на уровне DTO (Pydantic).
- Для каждого эндпоинта определены типовые коды ошибок (400, 404, 409 и т.д.).
- При попытке создать дубликат — ошибка 409 Conflict.
- При попытке удалить используемый шаблон — ошибка 409 Conflict.
- При ошибках доступа к хранилищу, RPC или БД возвращается статус `error` с подробным описанием.

## Мониторинг

- Логгирование всех операций (создание, удаление, ошибки) через общий логгер системы.
- Возможность интеграции с системой мониторинга через события RabbitMQ или экспорт метрик.

---

## События

- Публикация событий в систему (RabbitMQ): создание шаблона (`template.created`), удаление (`template.deleted`), изменение статуса (`template.status_changed`).
- Возможность подписки других модулей на эти события для автоматизации или оповещения.

---

## Тестирование

- Покрытие юнит-тестами всех основных путей (создание, удаление, обновление, ошибки).
- Интеграционные тесты взаимодействия с другими модулями (Volume, Storage, RPC).
- Использование моков и тестовых double-объектов для симуляции хранилищ и внешних сервисов.
- Запуск тестов через pytest, поддержка параллельного исполнения.
