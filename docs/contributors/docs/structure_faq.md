# 📚 FAQ по структуре документации OpenVair

> Этот документ определяет, **где и какие типы документации хранить**  
> в проекте OpenVair (или любом подобном), чтобы поддерживать порядок,
> масштабируемость и предсказуемость для пользователей, разработчиков и
> контрибьюторов.

> **Цель**: Обеспечить единый, полный, поддерживаемый подход к документации для
> любого нового и существующего функционала платформы.

---

## Руководство пользователя (User Guide)

- **Что:** Пошаговые инструкции, сценарии, FAQ, UI, описание пользовательских
  ошибок, как выполнять основные задачи.
- **Где:** `docs/user_guide/`
- **Примеры:**
    - `user_guide/index.md`
    - `user_guide/virtual_machines/index.md`
    - `user_guide/volumes/index.md`
    - `user_guide/backup.md`
    - `user_guide/faq.md`

---

## Технические требования к модулю

- **Что:** Ограничения, интерфейсы, сценарии, связи с другими модулями,
  требования к данным, API, ограничения, интеграционные детали.
- **Где:** `docs/reference/modules/<module>/tech_requirements.md`
- **Пример:**
    - `reference/modules/volume/tech_requirements.md`
    - `reference/modules/template/tech_requirements.md`

---

## Спецификация модуля

- **Что:** Описание внутренней архитектуры модуля, слоёв, бизнес-логики, API,
  схемы данных, структуры файлов, паттернов, ошибок.
- **Где:** `docs/reference/modules/<module>/specification.md`

---

## Подход к тестированию модуля

- **Что:** Как тестировать этот модуль: подход, сценарии, структура тестов,
  фикстуры, интеграция в CI.
- **Где:** `docs/reference/modules/<module>/tests_specification.md`

---

## Общие гайды по архитектуре и паттернам

- **Что:** Принципы DDD, описание архитектурных слоёв, общие шаблоны
  проектирования, устройство платформы.
- **Где:** `docs/architecture/`
- **Примеры:**
    - `architecture/index.md`
    - `architecture/general_terms.md`
    - `architecture/general_module/adapters.md`
    - и т.д.

---

## Общие подходы к тестированию и процессам

- **Что:** Как делать вклад в проект, best practices по тестам для всех,
  требования к процессу Pull/Merge Request, соглашения по стилю.
- **Где:** `docs/contributors/`
- **Примеры:**
    - `contributors/tests.md`
    - `contributors/general.md`
    - `contributors/docs_structure_faq.md` _(этот файл)_

---

## Справочник / Reference

- **Что:** Спецификации модулей, подробности API, схемы, все технические детали
  для разработчиков и архитекторов.
- **Где:** `docs/reference/`
- **Примеры:**
    - `reference/index.md`
    - `reference/api.md`
    - `reference/modules/volume/specification.md`

---

## Введение, быстрый старт, установка

- **Что:** Системные требования, назначение, как развернуть, как обновить,
  первый запуск.
- **Где:** `docs/getting_started/`
- **Примеры:**
    - `getting_started/index.md`
    - `getting_started/install.md`
    - `getting_started/update.md`

---

## Частые ошибки

- **Не помещайте технические требования к модулю в раздел архитектуры.**
- **Не смешивайте user_guide с reference — пользовательские сценарии отдельно от
  инженерных спецификаций.**
- **Не кладите тестовую документацию по модулю в contributors/tests.md — там
  только общий подход.**

## Обязательные виды документации для нового функционала

**При добавлении любого нового функционала (feature/module/endpoint) должны быть
созданы:**

1. **User Guide** — Описание сценариев использования, шагов для пользователя,
   новых UI, CLI, ошибок, типовых workflow.
   Обеспечивает конечных пользователей, операторов и интеграторов быстрым
   стартом и ясным пониманием сценариев работы.
   ⮕ Без этого пользователи не смогут эффективно использовать функционал.
2. **Технические требования** — Что должен обеспечивать модуль, с какими
   компонентами взаимодействует, ограничения, зависимости.
   Гарантирует, что новые модули/фичи соответствуют архитектуре проекта, не
   нарушают контракты и масштабируемы.  
   ⮕ Без этого сложно понять рамки изменений и проверить интеграцию.

3. **Спецификация (Архитектура и API)** — Архитектурные детали (слои, DDD),
   структура кода, эндпоинты, бизнес-логика, схемы данных.
   Даёт подробную карту реализации для ревьюеров, будущих разработчиков и
   аудита.  
   ⮕ Без спецификации сложно поддерживать и расширять код, повышается риск
   багов.

4. **Тестовая спецификация** — Как тестируется функционал: виды тестов,
   сценарии, структура тестовых файлов, требования к окружению.
   Делает поведение модулей проверяемым, снижает риск регрессии, ускоряет CI/CD,
   позволяет автоматизировать контроль качества.  
   ⮕ Без тестовой спецификации теряется доверие к качеству и сложно развернуть
   автоматическое тестирование.

5. **Обновление справочника** — Добавление новых модулей в `reference/index.md`,
   обновление навигации в mkdocs.yml/nav.
   Гарантирует, что все разделы доступны из единого nav, и никто не потеряется в
   структуре проекта.

---

## Как правильно вносить изменения в документацию

1. **В любой MR/PR, добавляющий функционал, обязательно включай соответствующие
   изменения в документацию.**
2. **Измени/дополни сразу все уровни:**
    - User Guide (новые сценарии, как использовать)
    - Reference/modules/… (требования, спецификации, тестовая документация)
    - Архитектурные гайды — если принципиально новая архитектура
    - CHANGELOG, nav, index-файлы
3. **Описывай в MR, какие разделы docs ты обновил и почему.**
4. **Делай ссылки между файлами (на примеры, подробности, reference), если
   разделённая информация.**
5. **Запусти локально сборку mkdocs и проверь, что всё отображается корректно и
   навигация работает.**
6. **Если есть автоген документации (swagger, typedocs) — обнови и его.**

## Советы по поддержанию актуального состояния документации

- **Обновляй документацию одновременно с кодом — не отдельным коммитом позже.**
- **Используй шаблоны pull/merge request — с чеклистом по документации.**
- **Периодически запускай ревью docs — смотри на “устаревшие” разделы, исправляй
  dead links, обновляй схемы.**
- **Добавляй примеры (snippets, curl, httpie, UI walkthrough) прямо в md-файлы —
  это снижает риск разночтений между кодом и docs.**
- **Веди список “outdated sections” — например, в виде issues с тегом
  documentation.**
- **Внедряй линтеры и автосборку docs в CI (например, mkdocs build --strict) для
  раннего обнаружения проблем.**
- **Документируй даже внутренние refactoring, если они затрагивают логику или
  API.**
- **Назначай ответственных за разделы документации, если команда большая.**
- **Добавляй документацию к новым ошибкам, edge-кейсам, ограничениям — сразу
  после внедрения.**
