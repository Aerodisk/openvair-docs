# Как оформлять документацию для существующего модуля

> Этот гайд обязателен для всех, кто добавляет или дорабатывает функционал
платформы OpenVAIR.
Следуйте этим шагам — и ваши изменения останутся понятны, воспроизводимы и
поддерживаемы!

## С чего начать?
- Изучи код и архитектуру модуля (или поговори с автором/разработчиком).
- Определи, кто основной пользователь: оператор, разработчик, интегратор, админ,
CI/CD, тестировщик?
- Собери основные сценарии использования (user story, бизнес-логика).

## Какие виды документации обязательны?
   **ВНИМАНИЕ:**
   Для любого значимого изменения/функционала должны быть оформлены следующие
   типы документации:

### User Guide
_“Как этим пользоваться?”_
- Для пользователей, операторов, devops, QA.
- Простые инструкции: как создать, удалить, настроить, получить доступ.
- Примеры UI, CLI, REST, сценарии, частые ошибки.

### Technical Requirements
_“Какие есть ограничения и особенности?”_
- Всё про лимиты, совместимость, версии, железо, зависимости.
- Описывает, какие условия должны быть выполнены для работы модуля.
- Почему модуль не работает “иначе”.

### Specification
_“Как это устроено внутри?”_
- Подробная архитектура, описание компонентов, классов, паттернов, data-flow.
- Внутренние API, эндпоинты, схемы, структура БД, бизнес-правила.
- Кто и как вызывает модуль, пример кода, взаимодействие с другими.

### Test Specification
_“Как проверить, что модуль работает как надо?”_
- Как запускать тесты (ручные и автоматические).
- Какие сценарии должны быть покрыты тестами (CRUD, ошибки, edge-cases).
- Как убедиться, что изменения не сломали старый функционал.

### FAQ / Known Issues / Cross-links
- Частые вопросы, грабли, обходные пути, ссылки на связанные разделы и модули.

## Как вносить изменения в документацию

1. Любое изменение в коде = проверь, нужна ли правка в docs!
    - Новое API, сценарий, CLI, UI, конфиг — почти всегда да!
    - Рефакторинг без внешних изменений — иногда нет, но лучше объяснить “почему docs не нужны”.
    
2. Параллельно с кодом оформи отдельный PR в docs-репозиторий.
    - В описании кода обязательно приложи ссылку на PR с документацией.
    - Если docs не нужны, явно напиши причину (“Ничего не менялось снаружи”).

3. Добавь новые разделы в nav (mkdocs.yml) и свяжи с index.md.
4. Попроси ревью документации — не мержи “втихаря”!

## Пример шаблонов для reference/modules/<module>:
- `index.md` — Краткое описание и навигация.
- `tech_requirements.md` — Технические ограничения и особенности.
- `specification.md` — Архитектура, слои, взаимодействие.
- `tests_specification.md` — Покрытие тестами и проверка.
- `faq.md` — Часто задаваемые вопросы (если есть).

## Почему важно оформлять ВСЕ типы документации?
- Без user_guide никто не разберётся, как работать с новым функционалом.
- Без technical requirements разработчики и операторы будут наступать на грабли,
не зная ограничений.
- Без specification будущие разработчики не поймут, зачем и как работает модуль,
как его развивать и интегрировать.
- Без тестовой спецификации ты рискуешь сломать что-то незаметно для всех
остальных.
- Без FAQ и кросс-ссылок люди будут плодить одинаковые вопросы и баги.

**ВАЖНО:**
> “Документация — это часть продукта, а не побочный файл!”
Пиши её так, чтобы спустя полгода любой коллега (и ты сам) мог быстро
разобраться, что происходит в проекте.
